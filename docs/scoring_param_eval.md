# 打分实验：gap 罚分 × allowBackToBackGaps（G3a，simTest）

2026-11-04。

## 1. 动机

`baseline_fn_attribution.md` §3e 的结论是：近距离错位（≤100 bp，simHuman–simMouse 上占真值 18.3%）里，96% 在 HoxD55 + 400/30 的打分下，预测路径的分本来就不低于真值路径。真值路径开 gap 更多，多付的罚分抵不上多赚的替换分。由此推测：调低 gap 罚分可能把这部分错位找回来。

同时测 `allowBackToBackGaps`：允许插入后紧接删除，或删除后紧接插入。

## 2. 实验设置

- 服务器同 `nlchain_progress.md` §10（`PROJECT_ROOT`）。simTest 10 个物种对，每组 20 个作业；运行用 `scripts/run_tune.sh`，评测用 `scripts/eval_tune.sh`（mafComparator 10M 样本，两份真值），汇总用 `scripts/tune_report.py`。
- 固定 G3a 配置：`--nlchain --inner=2000 --gappedthresh=2000`。公共参数不变：HoxD55、`--hspthresh=2200`、`--ydrop=3400`、`--masking=50`。只改两样：
  - `--gap=O,E`，O ∈ {100, 200, 300, 400}，E ∈ {20, 30}。命令行的 `--gap` 覆盖 `HoxD55.q` 中的 400/30（`lastz.c` 中读入打分文件之后的覆盖逻辑）。
  - 二进制：`bin/lastz_sc` 或 `bin/lastz_sc_b2b`。
- gap 罚分只作用于 gapped 延伸和比对计分（因此也影响 `--gappedthresh` 过滤）。种子、HSP、nlchain 串链和重新串链的 gap 代价表都不受影响；重新串链的块分只用替换矩阵。
- 二进制：`git archive 07e0f6f` 解到 `external/lastz-07e0f6f`（上传后核对 md5），由 `scripts/bootstrap_sc.sh` 构建，gcc 13.1，`-Werror`，sha256 记在 `bin/MANIFEST_sc.tsv`。
  - `bin/lastz_sc`：默认构建，sha256 `7d441492…793443`。
  - `bin/lastz_sc_b2b`：`make lastz allowBackToBackGaps=ON`，sha256 `edeecf96…fe693f`。simTest 不需要 `lastz_32`。
- 参数组 `gp_O<o>E<e>[_b2b]` 共 16 组，追加在 `config/tune_groups.tsv` 末尾。备份：`logs/tune_groups.tsv.bak_gap`、`logs/long.tsv.bak_gap`。运行脚本 `logs/gap_run.sh`：两个二进制各 40 线程同批并行。

## 3. 验证

- 构建与测试：`nlrechain_test` 2,929,359 项检查、`nlchain_test` 518,512 项检查，都是 0 失败；`base_tests` 19 项 SUCCESS；构建日志无 warning。b2b 版的编译命令含 `-DallowBackToBackGaps`，`--version` 显示 `allowBackToBackGaps=ON`。
- 冒烟（pseudocat vs pseudopig，G3a 参数）：
  - `lastz_sc` 与 `lastz_nli_d6a` 输出一致；
  - `--gap=400,30` 与不给 `--gap` 的输出一致；
  - `--gap=100,20` 改变了输出；
  - "插入紧接删除"的次数：O=100 时 b2b 版 4 处、默认版 0 处；O=400 时两版都是 0。
- **同批对照**：`gp_O400E30` 的 20 个 MAF（去掉 `#` 行）与 `nli_d6a_g3` 逐字节一致，R/P/F 与已知的 G3a 相同。

## 5. 结论

1. **调低 gap 罚分在这套参数下只有坏处。** 最温和的一档 400/20 已经让 F_np 下降 0.043：recall +0.015，precision −0.084，碱基重复使用从 0.02 升到 0.10。O ≤ 300 时 gapped 延伸越过相变点，比对冲进非同源序列，precision 跌到 0.09–0.54，CPU 增加到 16–28 倍，O=100 连作业都跑不完。§3e 那部分"打分最优的错位"，靠降低仿射 gap 罚分救不回来：在非同源序列上多开出来的假 gap，远多于修正的错位。
2. **相变的推断**：HoxD55 在随机序列上每列的期望分约为 −30。gap 便宜后，DP 可以靠频繁开 gap 去凑匹配，在非同源序列上的分数漂移变成不为负，y-drop 3400 剪不住，延伸一路走下去。这与截断次数、块长和内存的变化一致，但没有直接测漂移。
3. **O=300 比 O=200 还差（F 0.16 对 0.56），原因未核实。** O=200 的截断更多、输出的块更少、比对更短（中位 176 bp 对 663 bp），可能是失控的比对在回溯截断或重新串链时被丢得更多。两档都已失控，这一点不影响结论 1。
4. **allowBackToBackGaps 基本不起作用。**
   - 400/30 下 20 个 MAF 与不开时逐字节一致，1.06 亿列中插入紧接删除的次数为 0；400/20 下 20 个 MAF 只有 1 个不同，次数同样为 0；200/20 下 1.41 亿列中只有 51 次。
   - 原因可以直接算：相邻的插入 k 与删除 m（k ≥ m）可以改写为插入 k−m 再加 m 列替换。前者比后者多付 O + m(2E − 100)，HoxD55 的最差替换分是 −100。E=30 时要 m ≥ O/40 才划算，O=400 时就是 m ≥ 10，也就是两侧各 ≥10 bp 的成对 indel 紧挨在一起，很少见。
   - 在评测上看不出差别（F 差 ≤ 0.0003）。CPU 在 O ≤ 300 时比不开高 2–10%（同批运行，但没有重复测量）。
5. 第一批结束时的判断是"推荐配置不变"。第二批发现 500/30 更好，见 §5b。不开 b2b 这一条不变。

## 5b. 第二批：提高 gap 罚分（2026-11-04）

- 参数组 `gp2_O400E30`（同批对照）、`gp_O400E40`、`gp_O500E30`、`gp_O500E40`、`gp_O600E30`、`gp_O600E40`，不开 b2b，二进制 `bin/lastz_sc`。运行脚本 `logs/gap2_run.sh`：60 线程，有作业失败也会继续评测。备份：`logs/tune_groups.tsv.bak_gap2`、`logs/long.tsv.bak_gap2`。

结论：

1. **500/30 比 400/30 好**：F_np +0.0041、F_anc +0.0016，10/10 个物种对两项都提高，远缘对提高得更多（Cow-Mouse F_np +0.0061，Mouse-Rat +0.0022）。recall 降 0.011，precision 升 0.018，碱基重复使用也降了（0.019/0.011 → 0.014/0.006）。CPU 略低（−2.5%，同批）。
2. **E 是更敏感的参数**：E=40 在三档 O 上都比 E=30 差（F_np −0.003 ~ −0.011）；600/30 也已经低于 400/30。所以在 E=30 上，最优点落在 O 的 400–600 之间，靠近 500。E 在 30 附近（25、35）还没测过。
3. **还没分开的混淆**：gap 罚分升高后，同一条比对的分会降低，相当于收紧了 `--gappedthresh=2000`。500/30 的 precision 提高，有一部分可能来自门槛效应，而不是 indel 放置更准。要分开，需要在 400/30 下把门槛提高到某个值，使输出的碱基对数与 500/30 相近，再比较 F。
4. 收益约 +0.004，量级与 `--gappedthresh=2000`（G3b）、`--inner` 的单项收益相近，比降低罚分时的变化小得多。这说明 400/30 离最优点不远，在仿射 gap 模型里调参的空间就这么大。

## 6. 未解决 / 风险

- 500/30 的收益里门槛效应占多少还没分开（§5b 结论 3）；O ∈ {450, 550}、E ∈ {25, 35} 的细扫也没做。
- 降低 gap 罚分的同时缩小 ydrop 或换矩阵，有可能避开相变，但这样就成了多因素联动，本批没做。
- O=300 比 O=200 更差的具体机制没有核实（结论 3）。
- `run_tune.sh` 在有作业失败时直接退出，`gap_run.sh` 没有自动进入评测，评测是手动对完整的组补跑的（`logs/gap_eval1.log`、`logs/gap_eval2.log`）。O=100 留下的部分输出在 `runs/tune/gp_O100*`，失败作业有 `.failed` 文件。
- `tune_report.py` 每次运行都会重写 `results/tune/long.tsv`；改动前的版本在 `logs/long.tsv.bak_gap`。
- 服务器上的新文件只在服务器上：`scripts/bootstrap_sc.sh`、`logs/gap_run.sh`、`logs/gap2_run.sh`、`logs/gp_groups.tsv`、`logs/gp2_groups.tsv`、`bin/lastz_sc*`、`external/lastz-07e0f6f`。
