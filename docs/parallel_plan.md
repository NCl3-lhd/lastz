# 多线程与常数优化：`--threads`（2026-11-07）

目标：远缘推荐配置的输出逐字节不变，墙钟时间降到原来的 1/10 左右。

```
--hspthresh=2200 --gappedthresh=6000 --ydrop=3400 --masking=50 --scores=HoxD55.q --ambiguous=iupac --format=maf
--nlchain --inner=1000 --gappedthresh=1000 --gap=500,30 --realign=400,8 --mea=2,0.5
```

## 1. 基线：各阶段耗时

- 二进制：`bin/lastz_par0`（d92e055）；剖析版 `bin/lastz_par0_prof`。
- 服务器：`results/par/par0`、`results/par/par0_prof`。

| 阶段 | full_chrO（simHuman 191 Mb vs simMouse.chrO 6.9 Mb） | HM_chr0（simTest） |
|---|---|---|
| 种子搜索 + 无 gap 延伸 | 569 s（93%） | 56.3 s（61%） |
| 建种子表 | 16.2 s（2.7%） | 0.7 s |
| realign + MEA | 12.7 s（2.1%） | 21.3 s（23%） |
| gapped 延伸 | 8.3 s（1.4%） | 11.8 s（13%） |
| 读 target | 3.7 s | 0.2 s |
| nlchain（两次串链 + 重新串链） | 0.9 s | 1.3 s |
| 合计（剖析版） | 611 s | 92 s |

正式版墙钟：full_chrO 678 s；HM_chr0、CR_chr0、MR_chr0 分别为 92–112 s（两次运行负载不同）。

## 2. 依赖关系

- **query 序列之间、正负链的 finish 之间是串行的**：
  - `--masking=50` 在每条链输出后改写 target（写 `'x'`，并从种子表删种子）；
  - 下一条 query 的种子搜索、同一 query 正链的 gapped/realign 都会读到这些改写；
  - MAF 文本直接打印 target，所以 `'x'` 也会出现在输出里。
  - 因此不能按 query 拆进程，只能在进程内并行。
- **种子搜索**：唯一的串行状态是对角线哈希 `diagEnd[h]`，按 `(pos1-pos2) & 65535` 分为 65536 类。
  - 命中是否跳过、左延伸停在哪里，取决于同类之前的命中；
  - 右延伸是纯函数，状态只增不减。
- **realign/MEA**：每条比对独立，切点只取决于这条比对自己的 edit script。
- **建种子表**：每个词的链只和这个词的出现位置有关，不同词互不影响。
- **gapped 延伸**：一条链内严格串行（按分数从高到低，已有比对会约束后面的）。本次未并行。
- **`--inner` 窗口**：彼此独立，但在基线中只占约 0.1 s，没有并行。

## 3. 实现

线程库用 klib 的 `kthread.c`（`kt_for`，取自 minimap2 543fa12 的副本，未改动）。`--threads=N` 默认 1；N 为 1 时所有路径与原来相同。

### 3.1 种子搜索（`seed_hit_search_threaded`，`seed_search.c`）

1. 把 query 切块（默认约每线程 4 块，块长不短于 64 kb）。工作线程用 `kt_for` 从空的对角线哈希开始独立搜索每块，记下产生的 HSP，以及两个快照点（块首后 1 kb、16 kb）之后的摘要。
2. 主线程按块的顺序拼接：
   - 用块首的真实哈希状态 Tin 串行重放到第一个快照点 P，得到真实状态 T_P；
   - 用摘要检查 P 之后的每个决定（跳过还是延伸、左延伸停在哪里）是否与 T_P 下一致；
   - 一致就采用工作线程在 P 之后的结果，块尾状态为 max(T_P, e)；
   - 不一致就继续重放到下一级快照点，最后一级也失败则重放到块尾。
3. 摘要的推导见 `seed_search.c` 开头"多线程种子搜索"的注释。每类记四个量：
   - `lp`：快照点处的本地值；
   - `e`：快照点之后的 extent 最大值；
   - `minM`：本地延伸的命中的 min(种子起点, 左延伸到达点)；
   - `needSkip`、`blocked`：只因 lp 跳过的命中、左延伸被 lp 挡住的命中。
4. 对 reporter（`collect_hsps`）的调用全部在主线程上、按原顺序进行，所以 anchors 表与单线程逐字节相同。
5. 工作线程最多领先主线程 2N+2 块，用来限制同时存在的摘要（每块约 3 MB）。
6. 适用条件：`process_for_simple_hit` + x-drop 延伸 + 固定分数门槛，不做自比对，不限搜索次数，不是半权或分辨位种子。其他情况退回单线程。
7. 调试用环境变量（只影响切块和快照点，不影响结果）：
   - `LASTZ_PAR_CHUNK=<bp>`：块长；
   - `LASTZ_PAR_SNAP=<bp>,<bp>`：两级快照点离块首的距离；
   - `LASTZ_PAR_REPORT=1`：在 stderr 报告每级快照点采纳的块数。

### 3.2 realign/MEA（`realign_aligns_threaded`，`realign.c`）

- 工作区改为线程局部变量。
- `mea_prepare` 的缓存在开线程前设好，之后只读。
- 每个线程跑一条 lane，按原子计数领取比对；lane 结束时释放本线程的工作区。

### 3.3 建种子表（`build_seed_position_table_threaded`，`pos_table.c`）

- 第 t 个线程只登记 `packed*N/wordEntries == t` 的词。
- 每个线程都扫一遍 target，写入的 `last[]`、`prev[]` 元素互不相交。
- 每个词的链仍按位置从左到右前插，与串行相同。

### 3.4 常数优化

- **查表批处理加预取**（采用）：
  - 同一 query 位置的全部命中（精确加 12 个转换）先按原顺序收集起来；
  - 对它们在 target 中的位置发预取，再按原顺序交给 processor。
  - 本地片段（11 Mb target）上单线程 15.4 s → 11.3 s。
- **x-drop 循环 4 列一块、去分支**（未采用）：与逐列结果相同，但本地片段上没有可测的提速（11.34 → 11.33/11.49 s），已撤回。

### 3.5 已知限制

- 剖析版（`collect_stats`/`dbgTiming`）的计数器在多线程下有竞争、数值偏少。只影响 `--stats` 和计时输出，不影响比对结果；要准确计数请用 `--threads=1`。
- 主线程负责拼接，工作线程数为 N，所以种子阶段实际有 N+1 个线程，主线程大部分时间在等待。

### 3.6 剖析版在多线程下不可用来计时

`collect_stats`/`dbgTiming` 的计数器是共享全局变量。多线程时热点循环里的 `++` 争用同一缓存行，速度慢好几倍：

- `lastz_par2_prof --threads=16` 跑 full_chrO 用了 260 s，正式版只要 63 s；
- 其中建种子表 51 s，因为 `add_word` 里有计数。

所以多线程下的阶段占比只能用单线程剖析数据和正式版墙钟来推算。

## 4. 验证

### 4.1 本地（OrbStack VM，gcc 11.4，`-Werror` 0 警告）

基线为 HEAD（d92e055）构建，比较 stdout 去掉 `#` 行后的内容。

- **小数据对拍**（test_data），216 次运行全部一致：
  - 9 组参数：推荐配置、互换 target/query、默认参数、`--inner=2000` axt、`--nogapped`、`--masking=3`、`--chain`、多序列 reads、pseudopig2；
  - 6 种切块：默认、块长 1000/500/2000/137/37 bp，快照点从 0 bp 到 300 bp；
  - 线程数 1、2、4、8。
  - 极小块的设置下，各级快照点都有块失败，回退路径都走到了。
- **simTest 片段**（target simHuman 11 Mb，query simMouse.chr0 前 1.5 Mb，推荐配置）：
  - 线程数 1/2/4/8 × 三种切块，全部一致；
  - 默认切块下所有块都在第一级快照点（1 kb）通过；
  - 块长 5 kb、快照点 0/64 bp 时，300 块里有 139 块重放到块尾，输出仍一致。
- 并行建表加入后，小数据 216 次与 simTest 片段 1/3/8 线程也全部一致。

### 4.2 服务器（gcc 13.1，负载约 50–70/256）

- 构建：`bin/lastz_par1`（并行种子搜索、realign、批量预取）、`bin/lastz_par2`（再加并行建表）。

  - `realign_test` 26,784 项、`nlrechain_test` 2,929,359 项、`nlchain_test` 518,512 项检查 0 失败；

- **所有组的 MAF（去掉 `#` 行）与 par0 逐字节一致**。
- 每个作业单独运行，不与其他作业并行。

- **全基因组规模（full_chrO）**：16 线程 10.8 倍，32 线程 13.0 倍。
  - 单线程的批量预取提速 11%；
  - 并行建表在 16 线程时又省 13 s。
- **simTest 规模**（11 Mb target）：32 线程约 6 倍。
  - 剩下的主要是串行的 gapped 延伸（约 12 s）和 nlchain（约 1.3 s）。
- 多线程的 CPU 总量比单线程多 20–65%，来源是访存竞争（服务器同时有其他作业）和块首重放。

## 5. 未解决 / 下一步

1. **gapped 延伸仍串行**：simTest 规模要到 10 倍必须并行它。候选做法：
   - (a) 正负链的 finish 重叠：正链的 gapped 延伸只依赖负链 finish 之后的屏蔽，可以投机地并行算，负链屏蔽了碱基就重算。最多快 2 倍。要把 `gapped_extend.c` 的静态状态和回溯缓冲区改成每线程一份，并复制 query。
   - (b) 链内按分数顺序投机执行、按序提交：需要证明后加入的比对不影响已算的延伸，复杂度高。
2. 剖析版多线程计数不准（3.6 节）。如果需要，可把计数器改为线程局部，结束时汇总。
3. 种子阶段的 CPU 开销比单线程多 20% 以上，可以再查访存竞争（例如块的大小、预取距离）。
4. 只在 HoxD55 远缘推荐配置和 simTest/simMammals 上测过速度，正确性另在默认参数等 9 组参数上对拍过。
